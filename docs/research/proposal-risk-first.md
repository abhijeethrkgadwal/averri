# Survival-First Strategy: Build the Semantic Layer, Earn the Right to Build the Language

Core stance: every assumption that makes a new language attractive today (agents navigate badly, waste tokens, misread conventions) is eroding at roughly a yearly half-life. The only parts of the concept that *appreciate* as models improve are (a) verified facts about a codebase that no model can infer from text (contracts, effects, ownership, impact), (b) a neutral measuring stick, and (c) governance of what agents did. Build those. Treat the language as a projection you can turn on later, not a bet you must win now.

## 1. Product definition

**Ships first (months 0-6): "Lattice" — a compiler-maintained semantic graph with contracts, for existing TypeScript backends, exposed to every coding agent over MCP and CLI.** Concretely:

- `lattice init` on a Prisma/Drizzle + Express/Hono/NestJS repo produces `.lattice/graph.sqlite` plus a committed `lattice.json` snapshot: entities, fields, routes, handlers, validators, call/effect edges, with `origin: extracted` and a confidence score.
- Developers and agents add **verified facts** with lightweight TS annotations (`@requires`, `@ensures`, `@policy`, `@effects`, `@intent`, `@owner`) that compile to runtime checks, generated tests, and graph nodes with `origin: declared`.
- An MCP server + `lattice --json` CLI with ten tools (section 3), hard token budgets, root-cause-collapsed diagnostics, `impact`, and `explain_failure`.
- **AgentCodeBench v0** (30 tasks, public, pre-registered) released in the same quarter.

**Deferred:** the `.al` grammar, Langium LSP, code emitters for Drizzle/Hono/Zod, pg-boss workflows, the web Studio, Python extractor, any hosted runtime. All of these are unlocked only by a benchmark number (section 4).

**Positioning, one sentence:** *Lattice is the ground-truth semantic layer between your codebase and every coding agent: agents stop re-reading your repo, stop guessing your invariants, and you can see and govern what they changed.*

## 2. Language and representation decision

**Decision: IR is the product; the TypeScript-embedded typed DSL is the primary projection; a bespoke `.al` syntax is a deferred, optional second projection.** I am overruling the architecture brief's `.al`-first choice for survival reasons:

1. Wasp abandoned its DSL for a TS spec *with YC money and 8 people*; we have 2-3 people. Langium gives an LSP, but not formatter, Prettier/ESLint integration, Biome, tsc-based refactoring, or Copilot inline support, and every one of those is a day-one adoption blocker in a TS shop.
2. The no-training-data penalty is paid per context window forever. A TS-embedded form costs the agent nothing it does not already know; the semantics card for each construct (~300 tokens) is the only new knowledge.
3. The brief's strongest argument for `.al` (structured, domain-level diagnostics instead of tsc noise) is achievable without new syntax: the Lattice compiler evaluates a restricted TS module (no dynamic code, ts-morph extraction, reject anything non-literal), builds the IR itself, and emits *its own* diagnostics in domain terms. tsc runs afterward as a backstop, with cascades collapsed by mapping tsc errors back to IR nodes.
4. Agents in 2026 already use library-shaped DSLs (Convex, Encore.ts, Drizzle, Zod) competently. That is the existence proof.

**Human-readability guarantee** (enforced, not hoped for):
- One construct per concept, one spelling each, no sugar, no metaprogramming; `lattice fmt` enforces one field per line in a fixed key order so diffs read like a spec.
- `intent:` is a required field on every action and policy; the compiler rejects an action without it. PMs write intent; agents read it.
- `lattice docs` produces a read-only Markdown projection per module (entity tables, action cards with intent/policy/requires/ensures, event flow diagram) checked into `docs/`. A non-engineer must be able to review a PR from the Markdown diff alone; this is a release gate for the example app.
- The handler-line ratio is tracked on the reference app; if handler TS exceeds 40 percent of lines, the primitive set is too thin.

**Worked example** — real feature: "Add cursor pagination and RBAC to the Projects list endpoint in an existing Express+Prisma app."

Stage A (existing code, annotations only, week 1 of adoption):

```ts
// src/projects/list.ts (existing handler, unchanged logic)
import { contract } from "@lattice/core";

export const listProjects = contract("Project.list", {
  intent: "Members see projects of their own org only; admins see all. Cursor-paginated, newest first.",
  policy: ({ actor, input }) => actor.role === "admin" || actor.orgId === input.orgId,
  requires: { pageSizeBounded: ({ input }) => input.limit >= 1 && input.limit <= 100 },
  ensures:  { sameOrg: ({ result, input, actor }) =>
               actor.role === "admin" || result.items.every(p => p.orgId === input.orgId),
             stableCursor: ({ result, input }) => !input.cursor || result.items.length <= input.limit },
  effects: ["db:read"],
})(async (input, ctx) => { /* existing Prisma query */ });
```

From this alone, with no code generation, Lattice derives: a `Policy` node, two `requires`/`ensures` contracts linked to the `Exposure` for `GET /orgs/:orgId/projects`, an auth matrix test (anonymous/member-of-org/member-of-other-org/admin), a boundary test for `limit`, a runtime guard in dev/test, and an `impact` entry so that a later change to `Project.orgId` reports this action as dependent. Agents edit this file directly or via `apply_patch({op:"add-contract", target:"Project.list", ...})`.

Stage B (same feature, declared form, available only after the benchmark gate): `input`, `output`, and `paginate: { cursor: "createdAt", max: 100 }` are added, and the compiler generates the route, Zod schema, OpenAPI, and the Prisma/Drizzle query itself. The agent's text is a strict superset of Stage A; nothing is relearned.

## 3. Agent interface from day one

Transport: MCP over stdio (Claude Code, Cursor, Codex, Copilot, Amp all speak it) and `lattice <tool> --json` for agents that compose CLIs. `lattice init` writes a 40-line block into `CLAUDE.md`/`AGENTS.md`/`.cursor/rules` instructing the agent to call `overview` once, prefer `find`/`inspect` over grep for entities/actions/routes, trust generated tests, and never edit `@generated` files. This is how it works with every agent on day one without a plugin.

Tools, each with a hard `max_tokens` (default 1500), `detail: summary|full`, and cursors instead of full dumps:

| Tool | Returns |
|---|---|
| `overview` | stack, entry points, conventions summary, counts, health (uncovered routes, stale graph) |
| `find(query, kind?)` | `id \| kind \| path:line \| summary`, one line per hit |
| `inspect(id, include?)` | signature, intent, policy, contracts, effects, callers/callees as ids, tests, owner, last change |
| `impact(id \| patch)` | affected nodes with *why*, tests to run, migration y/n, API-breaking y/n |
| `conventions(topic)` | how this repo does errors/pagination/auth, one canonical example |
| `apply_patch(ops, dryRun)` | projected text diff + diagnostics |
| `check(scope=affected)` | typecheck + lint + affected tests, structured |
| `explain_failure(test \| diag \| trace)` | failing assertion with actual vs expected, causal chain, diff since last green, ranked fixes |
| `docs(construct)` | 300-token semantics card |
| `read_source` / `edit_source` | passthrough so the agent is never blocked |

Diagnostics are the feature with the strongest evidence behind them (RustAssistant-class results on structured errors with fixes): `{code, one-line message, node, path:line, cause, related ids, fix: {patch, confidence}, docs}`. Cascade collapse is non-negotiable: 40 tsc errors from one renamed field arrive as one diagnostic. Fixes come from a deterministic rule table keyed by code, not a model.

Trust rule: the graph is rebuilt on every file change (watch mode, <500 ms incremental target); every answer carries a `freshness` field and a `source` handle, so an agent can always verify. A stale graph that is trusted is worse than grep; staleness is treated as a P0 bug class.

## 4. Benchmark plan and the claim it must support

AgentCodeBench, as designed in the agent-cost brief, with one change in emphasis: **it is a product and a kill switch, not just marketing.**

- v0 at month 3: 30 tasks, three repo sizes, hidden HTTP-level acceptance tests, Express+Prisma and NestJS baselines written or audited by outsiders, three models, N=5, pre-registered analysis, tasks public.
- Arms: (A) plain stack + Claude Code with LSP; (B) plain stack + Lattice graph and contracts; (C) and (D) added only when a DSL exists.
- Metrics: pass@1 on hidden tests (primary), tokens on the jointly-solved subset split input/cached/output, tool calls, iterations, stuck rate, blinded readability.

**Claim that must hold for the business:** *Arm B raises pass@1 by at least 10 absolute points or cuts input tokens and tool calls by at least 30 percent on the jointly-solved subset, with non-overlapping CIs on at least two of three models.* If it holds, Lattice sells on evidence. If it does not, the governance and audit product still sells on visibility, and we have spent three months, not eighteen.

**Gate for the DSL:** build arm C/D only if arm B's gain plateaus below 30 percent on medium repos *and* the failure analysis shows the residual cost sits in layer mismatches and boilerplate that only derivation removes. Re-run quarterly with the newest frontier model; the delta must not be shrinking faster than we can ship.

## 5. Business model

**License:** Apache-2.0 for compiler, IR, MCP server, CLI, annotations runtime, benchmark harness; DCO, no CLA; explicit FAQ that generated output is unencumbered. Never relicense. The hosted control plane is closed.

**Free (individuals, any team size):** local graph, single repo, all tools, all diagnostics, generated contract tests, benchmark harness.

**Team, $25/dev/month (self-serve, capped at 50 seats):** hosted multi-repo graph, shared contracts across repos, impact reports posted on PRs, agent-change audit trail, token-cost dashboard per task/repo/agent.

**Enterprise, $60-250K/year:** SSO/SAML, RBAC, policy gates on agent edits ("no agent may remove a `policy`, touch `Payment*`, or merge a `@generated` edit"), VPC/on-prem, retention, SLA, private benchmark runs on their codebases, compliance packs later.

**First paid feature:** hosted graph + agent-change audit trail + impact-on-PR. A platform lead can expense it in one quarter, and it is buyer-based open core: ICs never lose a feature, managers pay.

**First ten customers:** 50-500 engineer companies, TypeScript monorepos, Prisma or NestJS, heavy Claude Code/Cursor spend with a named AI-enablement owner who has already been asked "why did our Claude budget run out in April." Found through the benchmark write-up, Prisma/NestJS communities, and direct outreach to companies publicly posting about agent token spend. Offer six months free Enterprise for benchmark data and a logo; convert at $30-80K.

**18-month milestones:**
- M3: extractor (Prisma+Express/Hono+Zod), annotations, MCP, AgentCodeBench v0 published with the arm A vs B number.
- M6: 1,000 stars, 200 weekly active repos, 3 design partners, NestJS extractor.
- M9: hosted graph, audit trail, dashboards; 5 paying Team accounts; benchmark at 60 tasks.
- M12: policy gates and SSO; 2 Enterprise deals ($100K+ combined); DSL go/no-go decision from benchmark data.
- M18: $400-800K ARR, 8-10 enterprise logos; if go, Stage B DSL alpha on the reference app with arm C/D numbers; if no-go, Python extractor and deeper governance.

## 6. Team and cost

- **Founder (you):** compiler/IR/MCP, benchmark design, design-partner sales. Non-delegable.
- **Engineer 2 (hire by M2):** extractors, hosted control plane, CI/PR integrations. Senior TS, has shipped a ts-morph or Babel tool.
- **Contractor, part-time (M2-M6):** baseline apps for the benchmark, written *outside* the team for credibility; later, Python extractor.
- **Skip or outsource:** auth (Better Auth/Clerk for the control plane), billing (Stripe), workflows (never build; compile to Temporal/Inngest later), DB hosting, design, a DevRel hire (the benchmark is the DevRel), fine-tuning, any Rust/WASM work.
- **Burn:** $22-32K/month (two salaries at modest founder rates, contractor $4-6K, infra and model API spend for benchmark runs $2-4K, legal/accounting). Eighteen months is $450-550K; bootstrap through M6 on design-partner services, raise a $1-2M pre-seed only after the M3 number exists.

## 7. Five biggest risks and how this strategy handles them

1. **Frontier models erase the navigation advantage.** We never sell navigation. We sell verified facts (contracts, effects, impact) that improve with better models (they write better contracts) and governance that matters *more* as agents write more of the code. The quarterly benchmark re-run is the early-warning system; the DSL is not started until the number justifies it.
2. **Model vendors or Sourcegraph/Augment/Cursor absorb the code graph.** Compete on semantics and neutrality, not retrieval: contracts and policy gates are not something Anthropic, OpenAI, or Cursor will build neutrally across competitors. MCP-native and CLI-native from day one so we are a complement inside every agent, never a competing agent.
3. **New syntax is not adopted (Wasp/Darklang pattern).** There is no new syntax in the first product; the declared form is TypeScript that every editor, linter, and model already handles. `.al` is a projection gated behind evidence, and the IR plus printer design means it can be added without migrating a single user.
4. **MDA-style round-trip rot in generated code.** Stage A generates only tests and runtime guards, never application code, so there is nothing to clobber. When Stage B emitters arrive, they are pure functions of the IR with `@generated` headers, content-hash writes, a `--clean` drift check in CI, `edit_source` refusing generated files, and a demoable `eject`.
5. **Adoption without revenue (Prisma/Encore trap).** Hosted stateful graph from M7, buyer-based open core from day one, and a hard rule that every OSS feature ships with a Team/Enterprise counterpart. The governance product sells on cost visibility even if the benchmark gain is modest; that is the floor under the company.

## 8. Why this beats the obvious alternatives

- **`.al`-first (architecture brief):** highest ceiling, binary outcome, 12 weeks before any user can try it on their own code, and it inherits Wasp's and Darklang's failure modes with a smaller team. This strategy keeps every piece of that design (IR, patch ops, diagnostics, test generation) and only changes the surface and the order.
- **Pure code-graph MCP (Stage 1 as written):** commoditized by free MCP graph servers and built-in LSP; no moat, no reason to pay. Contracts and impact are the difference between a free tool and a product.
- **Agent-spend observability alone:** fastest to revenue, but Helicone/Langfuse/Portal26 are already there and it has no path to the vision. Here it is a paid feature of the graph, not the company.
- **Hosted agent-native backend (Convex/Supabase lane):** $110M and $500M competitors, and it violates the no-lock-in principle. Compile to them later instead.
- **Vertical ERP (Keel's pivot):** revenue, but a services business that never produces a language.

The honest summary: the vision survives only if the first product makes money *without* the language, generates the logs that tell us which primitives deserve to exist, and owns the benchmark that decides whether the language is worth building. That is this plan.

# Critiques

## Verdict: viable-with-changes

Read as a language proposal, this is a surrender dressed as a strategy; read as a dev-tools business plan, it is directionally right and numerically fiction. Both readings matter because the founder asked for a language and the proposal's answer is 'later, if a gate fires' — and the gate ('arm B plateaus below 30 percent AND residual cost sits in layer mismatches') is a conjunction that the people running the benchmark have every incentive never to satisfy. Say what it is: a contracts-and-impact layer for existing TypeScript backends. That can be a company. It is not the company the founder described, and the document should stop pretending otherwise with lines like 'earn the right to build the language.'

The engineering core has one load-bearing contradiction. The proposal overrules the `.al` brief on survival grounds but keeps all of the `.al` brief's promises — derived auth matrices, fast-check properties from `ensures`, 'actual vs expected' explanations, impact analysis on what a contract reads — while replacing the decidable contract grammar with TypeScript closures. `policy: ({ actor, input }) => actor.role === 'admin' || actor.orgId === input.orgId` is opaque to a compiler. The same section says the compiler will 'reject anything non-literal.' Pick one: either define a decidable expression subset inside TS (and accept that tsc will not police the boundary, so you need your own checker and diagnostics — which is most of the `.al` work without the syntax benefits) or accept opaque predicates and downgrade every 'verified fact' claim to 'there is a predicate here.' The same leak appears in 'existing handler, unchanged logic': `contract(...)(async (input, ctx) => ...)` is a new calling convention, which means per-framework adapters for Express, NestJS, and Hono, plus app-specific fixtures (admin, member-of-other-org) for the 'generated' HTTP auth matrix — the hardest part of property testing against a database, dismissed in a single sentence. And the cold start is brutal: by the architecture brief's own numbers, contracts, policies, and events are 'essentially unrecoverable' from existing code, so `lattice init` yields Prisma entities the agent could already read in 2k tokens, and `intent` being compiler-required turns the first run on any real repo into a wall of errors.

On the 2027 question: the proposal asserts that contracts 'appreciate as models improve' and never argues it. The cost half of the thesis is being eaten by vendors for free — Codex persistent memory, Antigravity Knowledge Items, Cursor shared team indexes, and Claude Code explicitly choosing grep + LSP over embeddings. Cached input tokens are an order of magnitude cheaper than the cost framing assumes. The correctness half survives only if a verified `ensures` demonstrably beats a frontier model's own generated test; there is no argument for that here, and models that write better code write better tests.

The benchmark would not be believed and cannot be afforded as specified. N=5 against a documented 30x same-task variance will not yield 'non-overlapping CIs on two of three models.' The run matrix (30 tasks x 3 sizes x 3 models x 2 arms x 5) is roughly 2,700 agent sessions, $15-55K, against a stated $2-4K/month API budget. The comparison is confounded: arm B repos carry human-written contracts and intent, and the fair control is arm A plus an equally careful AGENTS.md and LSP, which is free. And it is vendor-run; the proposal itself dismisses Encore's benchmark on that basis. If you want this to be the measuring stick, give it to a neutral party and pay them.

The monetization is the weakest section because it charges for things the document elsewhere says are worthless. The hosted graph is a SQLite cache 'rebuildable from source in seconds' — there is no operational pain to buy relief from. A per-task token dashboard cannot be built from an MCP server, which never sees token counts; Claude Code, Cursor, and Copilot already export that telemetry to the enterprise's existing observability stack. 'Audit trail of agent changes' and 'policy gates on agent edits' need a reliable agent-vs-human signal that git does not have, and in practice reduce to CODEOWNERS plus a lint rule. The 'floor under the company' — governance selling on visibility alone — is the most crowded and least differentiated plank in the plan. The one feature with a plausible buyer is a GitHub App that posts contract-aware impact and auth-coverage reports on PRs; that is a $20/seat product, not $60-250K, and a two-person company with no SOC 2 will not clear enterprise procurement at M12 while hosting a semantic model of the customer's source code outside their VPC.

Team and timeline: the M3 list (five-framework extractor, annotation runtime, ten MCP tools with budgets, cascade collapse, explain_failure, and a published multi-model benchmark with outsider-written baselines) is six to ten engineer-quarters assigned to 1.5 people, one of whom is also doing sales. 'Bootstrap on design-partner services' contradicts 'six months free Enterprise for benchmark data.' The 'every OSS feature ships with a paid counterpart' rule halves velocity further.

What I would change to make it viable: (1) Narrow to one framework pairing (Prisma + NestJS or Prisma + Hono) and one vertical (multi-tenant SaaS with RBAC); delete the five-framework extractor. (2) Define a decidable contract subset inside TS with your own checker, or admit contracts are opaque and sell impact/coverage instead of verification. (3) Drop the hosted graph and dashboards; the first paid product is a PR bot (impact, policy coverage, contract regression) with a seat price, sold to teams, not enterprises, until there is a SOC 2. (4) Make the benchmark third-party-run, N>=20 on a smaller task set, with a documentation-matched control arm; budget it honestly. (5) Decide the language question now: either the TS-embedded form IS the language (then invest in the semantics cards, the checker, and the docs projection as first-class) or there is no language and the pitch should say so. (6) Cut M12 Enterprise targets; replace with 20 paying teams. The ideas worth the founder's time are the IR-with-verified-facts, the structured diagnostics, the token-disciplined agent interface, and the licensing stance; everything else in the plan needs to shrink by about two-thirds before it fits the team that has to build it.

### Fatal flaws
- The proposal quietly abandons the founder's actual ask and then hides it behind an un-triggerable gate. The DSL is built only if 'arm B's gain plateaus below 30 percent on medium repos AND the failure analysis shows the residual cost sits in layer mismatches and boilerplate.' That is a conjunction of a negative result and a specific attribution finding, evaluated by the people who do not want to build the language with 1.5 engineers. It will never fire. Say plainly: 'we are not building a language; we are building a contracts-and-impact layer for TypeScript repos.' Either that is the company, or the founder should reject this plan.
- The 'annotations on existing code, unchanged logic' claim is false and is the exact abstraction leak the proposal says it avoided. `contract("Project.list", {...})(async (input, ctx) => ...)` is a runtime wrapper with a new calling convention (`input`, `ctx.actor`), not an annotation. Express handlers are `(req, res)`, NestJS actions are DI-injected decorated methods, Hono is `(c)`. Every framework needs an adapter that extracts `input` and `actor` from the request, and the generated 'auth matrix test over HTTP' needs app boot, DB seeding, and actor fixtures (anonymous / member-of-org / member-of-other-org / admin) that only the app knows how to construct. That fixture problem is the hardest part of property testing against a database and is hand-waved in one sentence ('derives... an auth matrix test').
- Contracts-as-TypeScript-closures destroy the semantics the product is sold on. The policy `({ actor, input }) => actor.role === "admin" || actor.orgId === input.orgId` is an opaque function. The compiler cannot derive an allow/deny table, cannot translate it to a fast-check property, cannot report 'actual vs expected' beyond 'returned false', and cannot do impact analysis on what the closure reads. The proposal also says the compiler will 'reject anything non-literal' — a closure is non-literal. So either you restrict to a decidable expression subset (now you have reinvented the `.al` contract language inside TS, with tsc unable to tell the agent it has stepped outside the subset) or you accept opaque closures and the 'verified facts' moat is reduced to 'there exists a predicate here.' The architecture brief's `.al` design was coherent precisely because it had a closed expression grammar; this proposal keeps the promises and discards the mechanism.
- Day-one value is near zero without human-written annotations, and the plan never budgets the annotation work. The architecture brief states Policy/Contract/Event/Workflow semantics are 'essentially unrecoverable' from existing code and Express route extraction is 50-80%. So `lattice init` yields Prisma entities (which an agent already reads from `schema.prisma` in ~2k tokens) plus low-confidence routes. The moat appears only once someone writes hundreds of `requires`/`ensures`/`policy`/`intent` blocks on a 15k-LOC repo. That is mypy-on-a-legacy-Python-codebase adoption economics: value proportional to annotation density, cost paid up front, and `intent:` being 'required... the compiler rejects an action without it' makes the first run on any real repo a wall of errors.
- The benchmark as designed is both underpowered and confounded, and would not be believed. (1) Power: the proposal's own brief reports 30x same-task variance; N=5 cannot produce 'non-overlapping CIs on at least two of three models' for a 10-point pass@1 gain. (2) Cost: 30 tasks x 3 repo sizes x 3 models x 2 arms x N=5 = 2,700 agent runs at $5-20 each is $15-55K for v0 alone, against a stated API budget of $2-4K/month. (3) Confound: arm B repos are pre-annotated with contracts and intent that a human wrote. The honest control is arm A plus an equally careful AGENTS.md and LSP, which is free; the proposal compares against 'plain stack' and will therefore measure the value of documentation, not of Lattice. (4) Credibility: it is vendor-run; the proposal itself dismisses Encore's benchmark as 'vendor-biased' and then proposes the same thing with a pre-registration document. No one has ever shut down a company because their own pre-registered benchmark failed; the 'kill switch' framing is theater.
- The paid tier charges for things the proposal says are worthless or that incumbents already give away. The hosted graph is a cache the architecture brief calls 'rebuildable from source in seconds' — there is no stateful operational burden (the Temporal/Supabase pattern) to pay to avoid; a 50-seat team will self-host a SQLite file. The 'token-cost dashboard per task/repo/agent' cannot be built from an MCP server, which never sees the model's token counts; it requires the agent's own telemetry, which Claude Code (OTel export), Cursor (team analytics), and Copilot (metrics API) already ship to the enterprise's existing Datadog/Grafana. 'Agent-change audit trail' and 'policy gates on agent edits' presuppose a reliable signal that an edit came from an agent rather than a human; git has none, and the practical implementation collapses to CODEOWNERS + branch protection + a lint rule, which GitHub already sells. That leaves 'impact-on-PR', which is a feature, not a $60-250K contract.
- The team, timeline, and procurement assumptions are not credible together. M3 requires an extractor for Prisma + Express/Hono + Zod, the annotation runtime, ten MCP tools with token budgeting, cascade-collapsed diagnostics, `explain_failure`, and a published 30-task, 3-size, 3-model, N=5 benchmark with outsider-written baselines — with the founder doing 'compiler/IR/MCP, benchmark design, design-partner sales' and engineer 2 hired 'by M2'. Then M12 calls for two Enterprise deals at $100K+ combined from a two-person company with no SOC 2 (a 6-12 month, $30-80K effort), selling a hosted service that ingests a semantic model of the customer's source code — the one thing security teams will refuse to let leave the VPC, which a two-person team cannot support on-prem. 'Bootstrap through M6 on design-partner services' also contradicts 'offer six months free Enterprise for benchmark data'; with 1.5 engineers you cannot do services and build the product.
- The 'appreciates as models improve' thesis is asserted, not argued, and 2026-2027 trends cut against the cost half of it. Codex has persistent memory, Antigravity persists Knowledge Items across sessions, Cursor ships shared team indexes, and Claude Code dropped embeddings because grep + LSP 'worked better.' The orientation bucket (25-55% of task cost per the agent-cost brief) is being removed by model vendors for free, and cached input tokens cost ~10x less than the proposal's cost math assumes. What survives is the correctness half (contracts), but models that write better code also write better tests, so the marginal value of a generated contract test shrinks too. The proposal needs a concrete argument for why a verified `ensures` beats a frontier model's own test in 2027; it offers none.

### Weak assumptions
- 'A TS-embedded form costs the agent nothing it does not already know.' The agent-cost brief explicitly says the expensive failure class is semantic, not syntactic: not knowing whether `requires` runs before or after `policy`, whether `transaction` covers the handler, what `cache` does on invalidation. A library-shaped DSL has the same semantic-unfamiliarity cost; only the syntax cost is gone. The ~300-token semantics cards are the real spec and must be in context, which the proposal charges to nothing.
- 'Graph rebuilt on every file change, <500 ms incremental target' for a ts-morph program over a 15-60k LOC repo. Full ts-morph project load is seconds to tens of seconds; incremental re-binding with call-graph effect edges is not a solved problem in ts-morph. 'Staleness is treated as a P0 bug class' means the team will spend its life on cache invalidation.
- 'Cascade collapse is non-negotiable: 40 tsc errors from one renamed field arrive as one diagnostic.' Root-cause attribution of arbitrary tsc error sets is a research problem; a deterministic rule table will cover three or four rename/field-type patterns and nothing else. Fine as a feature, overclaimed as a guarantee.
- `apply_patch` with IR ops projected onto TS object literals assumes agents want semantic edit operations. Every 2026 agent edits text through its own Edit tool and will route around a foreign patch op the moment it fails once. The architecture brief's projection printer + ULID reconciliation is weeks of work for a tool whose demand is unproven; and in the TS-embedded form there is no place to park ULIDs, so 'history by ULID across renames' silently degrades to 'string id changed = new node.'
- Contracts with side effects (`requires: db.Member.none(...)` in the worked example, `ensures: result.items.every(...)`) running as production guards. Each request now pays extra queries and full-result scans; the proposal mentions sampling only in the architecture brief. Also, importing `@lattice/core` wrappers into every handler is exactly the runtime lock-in the concept forbids; 'eject' becomes 'unwrap every action by hand.'
- 'Buyer-based open core... every OSS feature ships with a Team/Enterprise counterpart' halves OSS velocity for a team of two and has no precedent at that size; GitLab did it with hundreds of engineers.
- 'First ten customers: 50-500 engineer companies... with a named AI-enablement owner' assumes that persona has budget for a third-party graph service rather than for Cursor/Claude Code enterprise seats, whose vendors are bundling exactly the dashboards and policy controls listed here.
- Positioning 'the semantic layer between your codebase and every coding agent' is indistinguishable from Augment Context Engine, Sourcegraph, Unblocked, and Greptile copy. The differentiator (contracts/effects/impact as verified facts) is not in the sentence.
- Deferring Python while the research shows FastAPI and agent-provisioned Postgres are a large share of agent-written backends halves the addressable market before the first customer; and the extractor list (Prisma + Drizzle + Express + Hono + NestJS) is already five frameworks for one engineer.
- 'Three months, not eighteen' as the downside. By the time arm B numbers exist you have built the extractor, runtime, MCP server, diagnostics, and benchmark; that is the whole engineering of the company, not a cheap probe.

### Keep
- Order of operations: do not ship novel syntax first; treat the IR as the product and any surface syntax as a projection gated by evidence. This is the correct read of Wasp, Darklang, and the DSL literature, and it is the single most valuable decision in the document.
- Contracts, effects, ownership, and impact as compiler-verified graph facts, carrying `origin: extracted|declared` and a confidence score. This is the only part of the stack that free MCP graph servers, built-in LSP, and context engines do not have, and it is worth keeping even if everything else changes — provided the contract language is made decidable.
- Structured diagnostics with a root cause, related ids, and a suggested patch from a deterministic rule table. RustAssistant-class evidence supports it, and it is cheap relative to its value.
- Agent-interface discipline: hard token budgets per tool, ids-not-bodies by default, cursors instead of dumps, a `freshness` field and `source` handle on every answer, and `read_source`/`edit_source` passthrough so the agent is never blocked.
- The `intent` field and the read-only Markdown docs projection as the human-readability mechanism — as a recommendation and a release gate on the reference app, not as a compiler error on day one.
- AgentCodeBench's design principles: hidden HTTP-level acceptance tests, behavioral-equivalence baselines, reporting on the jointly-solved subset with input/cached/output split, a held-out task set authored after primitives freeze, and publishing losses. Keep the design; move the operation to a third party (a university group or a neutral benchmark org) and fund it as marketing.
- Licensing: Apache-2.0 for everything a developer types into or runs locally, DCO not CLA, never relicense, explicit statement that generated output is unencumbered. Correct and should not be reopened.
- The `eject` guarantee and the handler-line-ratio metric (if handler TS exceeds ~40% of lines the primitive set is too thin) as objective health checks on abstraction leakage.
- Compile `workflow`/`retry`/`queue` to Temporal/Restate/Inngest and `entity` to Drizzle/Prisma + Postgres rather than building a runtime. Owning none of the stateful infrastructure is right for this team size.
- The vertical-slice instinct (multi-tenant SaaS APIs with RBAC, billing, webhooks) — it should be narrowed further to one framework pairing and made the entire V0 scope.

## Verdict: viable-with-changes

Evaluated as the agent that would actually sit on the other end of this MCP server.

Would it make me faster, cheaper, more reliable than TypeScript plus good MCP tools? Yes on medium and large repos, mostly through three things: impact (a verified answer to "what else breaks if I change this"), cascade-collapsed diagnostics, and a fast structured check on affected tests. Those cut the fix loop, and the fix loop is where cost compounds because every iteration resends the whole context. The navigation tools (overview, find, inspect) are a smaller win than the proposal estimates. I will still read the exact source of anything I am about to edit, so ids-not-bodies saves the irrelevant reads, not the relevant ones; realistic orientation savings are 20-30% on medium repos and roughly nothing on small ones, where the MCP schemas and CLAUDE.md block (3-5k tokens per turn) make it net negative. Target customers (50-500 engineers, monorepos) are the right ones precisely because of this.

Where I would still burn tokens: re-reading source before edits; double-checking any graph answer whose precision is below ~95% (Express extraction at 50-80% is below the line, so I would grep anyway and pay twice); paging through 1500-token budgets, where each cursor fetch is a full-context round trip and is more expensive than one 4k answer; and learning the runtime semantics of contract(): when does ensures run, inside or after the transaction, what does it throw, does it run in prod. Semantics, not syntax, is what I do not know.

Would I hallucinate syntax? For the TS-embedded form, structure no, vocabulary yes: I would guess requires vs preconditions, policy vs authorize, the shape of the context object, the effects string vocabulary. tsc catches all of those, which is the whole argument for the TS-embedded decision and why it is correct. For the .al grammar in the architecture brief, yes, heavily: the annotation style (@paginate(cursor), @owned, retry 3 backoff exponential) is irregular across examples and I would reproduce it wrong in every context window that lacks the spec. Deferring it is right. For IR patch ops, also yes; I would not use apply_patch at all, I would edit the file. Drop it from v0 and keep impact(diff) plus dry-run diagnostics.

Three things need fixing before the pitch is honest. First, on existing repos the differentiating nodes (contracts, policies, effects) are unrecoverable by extraction and unverified when annotated, so day-one Lattice is a commodity code graph plus declarations nobody has written. Verify declared effects and writes with a static scan from the start, mark origins as extracted / declared / verified, and ship a suggest pass that drafts contracts from zod schemas, guards, and existing tests. Second, pick the contract representation: the worked example uses lambdas, the test-gen and impact plans need the decidable subset. Lambdas plus input-schema-driven property tests (contracts as oracle) is what I would choose; accept that you then cannot generate "an input that violates exactly this clause" or print to .al without a translation layer. Third, the benchmark is confounded: arm B repos contain intent and contracts that arm A lacks, and the pass@1 bar of 10 points hits a ceiling on tasks frontier models already pass at 80%. Give arm A the same text as comments, select tasks with 40-60% baselines, and keep the pre-registration.

Two agent behaviors the design should plan around. When a wrapped existing handler fails a new ensures in test mode, I will tend to relax the contract to get green; detect and flag contract weakening on PRs, which is both a safety net and the most sellable governance gate you have. And a wrong suggested fix with 0.8 confidence anchors me; only attach fixes to diagnostic codes whose repair is genuinely deterministic (missing policy, undeclared event), and for logic failures give me actual-vs-expected plus diff-since-green with no hypothesis.

Is the debugger design useful or noise? The explain_failure spec (failing assertion with values, triggering input, causal chain, diff since last green, nothing I already read this session) is exactly right and is signal. The ranked-hypothesis part is noise unless it is rule-table deterministic. Trace-per-action with phase records is useful for debugging policy denials and contract failures and is cheap to build.

Smaller changes I would want: raise the default budget for inspect and return the source span inline for short actions; make check fast or I will bypass it; collapse the three framework annotation forms to one object shape; make staleness refuse-or-rebuild rather than a flag; and ship pitfall rules (webhook raw body, idempotency, cursor pagination) as Stage A diagnostics because that is where my integration failures actually originate and it needs no language.

Verdict: the survival-first ordering is correct, the IR-as-product and TS-embedded decisions are the ones that make it usable by an agent today, and the diagnostics, impact, and check pieces are worth more to me than any syntax. With the verification gap closed, the contract representation decided, and the benchmark equalized, I would use this on a real repo and would expect it to shave the fix loop materially; without those changes it is a nicer code graph with a strong claim it cannot back.

### Fatal flaws
- Cold-start / 'verified facts' gap on existing repos: the architecture brief admits contracts, policies, events and effects are 'essentially unrecoverable' by extraction, and Stage A declares them via annotations that nothing verifies (effects: ['db:read'] is a string I will trust). So on day one the graph is a commodity code graph (entities/routes, which LSP+grep already give me) plus unverified opt-in annotations nobody has written yet. The pitch 'ground-truth semantic layer' is false until (a) a static scan verifies declared effects/writes against handler code and (b) a 'suggest' pass drafts contracts from existing zod/validators/tests so there is something in the graph in week one.
- Contract representation is contradictory: the proposal's worked example uses TS lambdas (result.items.every(...)) while the test-generation, impact, and .al-projection plans require the decidable expression subset (max depth 3, sum/count/exists). Opaque lambdas cannot be inverted to 'an arbitrary that violates exactly this clause', cannot be statically linked to fields for impact, and cannot be printed to .al later. This must be decided now: either lambda contracts with input-schema-driven property tests (contracts as oracle only) and no static field linkage, or a restricted expression language with an expressiveness cliff. Leaving it ambiguous means the test-gen and impact claims are overstated.
- The benchmark gate as designed will measure documentation, not Lattice: arm B repos carry human-authored intent, policies, and contracts that arm A lacks, so a 30% token / 10-point pass@1 gain would be indistinguishable from 'well-commented repo vs undocumented repo'. Additionally, 10 absolute pass@1 points is near-unreachable on tasks frontier models already pass at 70-85%; without equalizing documentation in arm A and selecting tasks with a 40-60% baseline, the kill switch will either falsely fire or falsely pass.

### Weak assumptions
- Orientation cost is 40-60% recoverable via ids-not-bodies: in practice I read the source span of anything I am about to edit anyway, because my edit tool needs exact text. inspect() saves the irrelevant reads (roughly a third of files), not the relevant ones. Expect 20-30% orientation savings on medium repos, near zero on repos under ~40 files where I just read everything, and net negative once 3-5k tokens of MCP schemas plus the CLAUDE.md block are charged every turn.
- I will use apply_patch with IR op vocabulary: I will not. It is a second mini-language (op names, target path syntax, phase keys) I have no prior for and will hallucinate; after any projected rewrite I must re-read the file to confirm what the printer actually produced, which erases the saving. I will edit the TypeScript directly.
- A confidence score makes a partially-correct extracted graph usable: trust is binary in operation. Below ~95% precision on 'who handles route X' I will verify with grep, which doubles cost rather than halving it. Express at 50-80% extraction accuracy is below that threshold; ship Prisma/Drizzle + NestJS/Hono first where extraction is >90%, and refuse to answer rather than answer with confidence 0.5.
- 1500-token default budgets with cursors are cheaper: every extra tool call is a full-context round trip, and input tokens dominate cost. One 4k response beats three 1.5k pages. Budget by relevance and let the default be larger for inspect; keep 800 for find.
- Dev/test-mode contract enforcement makes code more correct: when a wrapped existing handler starts failing an ensures, my observed behavior is to weaken the contract to get green, not fix the code. The proposal has no detection for 'agent relaxed a contract'. This is both a correctness risk and, flipped, the best governance gate you could ship (flag contract weakening on PRs).
- RustAssistant-class evidence transfers to explain_failure: that evidence is about compiler errors with structured codes, not semantic test failures. Deterministic fixes are appropriate for structural diagnostics (missing policy, undeclared event, dropped field); for logic failures, a 0.8-confidence 'ranked hypothesis' anchors me on a wrong fix. Only attach fixes to codes where the rule table is actually deterministic; for test failures ship actual-vs-expected plus diff-since-green and no fix.
- <500 ms incremental graph rebuild on real customer monorepos (100k-500k LOC) via ts-morph: unlikely. Stale answers mid-edit will occur; the freshness field helps only if stale answers are refused or auto-rebuilt, because I will not read a freshness flag on every response.
- 'One construct, one spelling' survives three framework integrations: a contract() HOF for Express/Hono, a decorator for NestJS, and whatever Drizzle/Prisma need will drift into three dialects, which is exactly the irregularity that produces syntax errors. Pin one object shape and make the Nest decorator a thin alias with identical keys.
- Agents will follow 'prefer find over grep' from CLAUDE.md: I will use both unless find wins on the first call. The instruction must be backed by find returning path:line in a form I can act on immediately, otherwise it is just extra context.
- The agent-change audit trail is differentiated: git blame already attributes edits; what is differentiated is semantic-level gating (removed a policy, widened a permission, touched Payment entities), so sell that and not the generic log.

### Keep
- IR is the product, the TypeScript-embedded form is the primary projection, and .al is deferred behind evidence. From my side this is the single decision that makes the thing usable on day one: my TS prior transfers, tsc catches key-name mistakes, and I need only a ~300-token semantics card per construct rather than a grammar in every context window.
- Cascade-collapsed structured diagnostics with deterministic, code-keyed fixes. Forty tsc errors from one renamed field arriving as one diagnostic with a patch is the highest-value feature in the whole proposal, and it needs no DSL.
- check(scope=affected) returning structured results. If it runs in under ~10 seconds it replaces my own tsc+vitest runs; if it is slower I will run them myself, so speed is the feature.
- explain_failure with actual-vs-expected values, the inputs that triggered it, the causal chain (action -> policy -> contract -> line), and the diff since the last green run, omitting stack traces and framework internals. That is the format of a useful failure.
- impact(id | diff) as a compiler-verified fact (affected nodes with why, tests to run, migration y/n, API-breaking y/n). This is the one thing no retrieval tool or LSP gives me and the thing I most often get wrong.
- A required intent field per action and policy. A recorded decision ('re-inviting a pending email resends') removes the 10-20% of cost that is re-asking ambiguity questions, and it is the layer a PM can review.
- The benchmark as a pre-registered kill switch with the A/B (and later C/D) arm design, tokens reported on the jointly-solved subset, input/cached/output split, N=5, and losses published. Add the documentation-equalized arm A.
- read_source / edit_source passthrough so I am never blocked, plus edit tools refusing @generated files and a CI --clean drift check. This is the correct answer to the MDA round-trip failure.
- lattice init writing a short block into CLAUDE.md / AGENTS.md / .cursor/rules. This is how the tool reaches me without a plugin and is cheap.
- Freshness on every answer with staleness treated as a P0 bug class; strengthen to refuse-or-rebuild rather than annotate.
- Encoded-pitfall primitives (webhook raw body, idempotency keys, cursor pagination off-by-one). These are where my integration failures actually come from; they can ship in Stage A as lint-style diagnostics plus a conventions() canonical example, no DSL required.
- Apache-2.0, DCO, never relicense, explicit statement that generated output is unencumbered; buyer-based open core where ICs never lose a feature.
