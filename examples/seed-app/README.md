# @averri/seed-app

The Averri reference application and the benchmark seed app (`docs/BENCHMARK.md` §2): a multi-tenant
SaaS backend in **Hono 4 + Prisma 6 + Zod 4** with organizations, memberships and roles, invitations,
projects and tasks, API keys, Stripe-style billing with a signed webhook, an audit log and cursor
pagination. It is a normal application first; the Averri declarations in `src/averri/` are attached in
observe mode and change nothing at runtime.

## Run it

```sh
# from the monorepo root (dependencies are installed there)
npx prisma generate --schema examples/seed-app/prisma/schema.prisma
cd examples/seed-app
npm run db:push        # creates prisma/dev.db (SQLite) from the schema
npm run db:seed        # loads the deterministic seed data set
npm run dev            # http://localhost:3000, hot reload
npm test               # vitest: hand-written tests and Averri's generated tests (tests/averri), one throw-away SQLite file per test file
```

Configuration is by environment (`.env.example`): `DATABASE_URL` (defaults to `prisma/dev.db`),
`PORT`, `STRIPE_WEBHOOK_SECRET`, optional `STRIPE_SECRET_KEY` (unset = in-memory fake Stripe client).

SQLite is the local/test database. Postgres is a one-line switch of the datasource `provider` in
`prisma/schema.prisma`; the schema uses no SQLite-specific features (closed string sets are `String`
columns validated by Zod and can become Postgres enums).

Seed users (password `password123`) and their fixed bearer tokens:

| user | role | token |
|---|---|---|
| owner@acme.test | owner of Acme | `usr_seed_owner` |
| admin@acme.test | admin of Acme | `usr_seed_admin` |
| member@acme.test | member of Acme | `usr_seed_member` |
| other@globex.test | owner of Globex | `usr_seed_other` |
| outsider@example.test | no organization | `usr_seed_outsider` |

API keys: `sk_seed_acme_member` (member scope), `sk_seed_acme_admin` (admin scope), both for Acme.

## Layout

```
prisma/schema.prisma          11 models; migrations/0001_init/migration.sql is applied by the tests
src/app.ts                    createApp(deps): middleware, route mounting, error envelope
src/server.ts                 @hono/node-server entry point
src/db.ts                     Prisma client factory (DATABASE_URL, injectable in tests)
src/auth.ts                   bearer-token resolution (user tokens + API keys), requireUser / requireOrgRole
src/context.ts                AppDeps (db, events, mailer, stripe, config, clock) and the Hono env type
src/events.ts                 in-process EventBus; events are named "averri/<Event>"
src/lib/                      errors, validation, cursor pagination, crypto, Stripe client + signatures, mailer, job engine
src/services/*.ts             business logic, one module per aggregate; every mutation is a transaction with an audit entry
src/routes/*.ts               38 Hono routes, thin: parse → authorize → service → json
src/workflows/                InviteFlow (custom job engine) consuming averri/MemberInvited
src/seed.ts                   deterministic seed data shared by db:seed and the tests
src/averri/*.ts                Averri declarations (observe mode): entities, policies, events, actions, queries, workflow, integration
averri.config.ts               defineConfig: entry points, auth middleware names, actor fixtures, emitter spy
test/*.test.ts                HTTP tests through app.request(): happy paths, auth matrix, webhook, pagination
test/setup-averri.ts           per-file seeded SQLite database for the generated tests (they import the default app from src/app.ts)
tests/averri/*.gen.test.ts     generated by `averri build`/`averri testgen` from the declarations; never edit them
```

### Conventions

- **Errors** are `AppError(status, code, message, details?)` thrown from services and rendered by
  `app.onError` as `{ error: { code, message, details? } }`. Zod failures are 400 `validation_failed`
  with `{ source, issues: [{ path, message }] }`.
- **Authentication** never rejects on its own: the `auth` middleware resolves `actor` (or `null`); handlers
  call `requireUser(c)` (401 / 403 `user_required` for API keys) or `requireOrgRole(deps, actor, orgId, roles)`
  (404 unknown or soft-deleted organization, 403 `not_a_member`, 403 `insufficient_role`).
- **Tenant scoping**: every organization-scoped row carries `organizationId`; services always query
  `{ id, organizationId }` so a row from another organization is a 404, never a leak.
- **Pagination**: list endpoints take `?limit=&cursor=` and return `{ data, nextCursor }` (keyset on
  `createdAt desc, id desc`; `src/lib/pagination.ts`).
- **Events** are published after the transaction commits with `deps.events.send({ name: "averri/<Event>", data })`.
  Workflows subscribe by that literal name; handler failures never fail the request.
- **Webhook** (`POST /webhooks/stripe`): signature verified over the raw body (`t=...,v1=...` HMAC-SHA256,
  300 s tolerance), idempotent by Stripe event id (`WebhookEvent` unique on `(provider, eventId)`),
  processed inside one transaction so a failure rolls back and Stripe retries; unknown customers and
  unhandled types are acknowledged as `ignored`.

## Averri declarations

`src/averri/` declares the application for Averri in **observe mode** (no `run`, every `route` matches a
real Hono registration): 11 entities with invariants, 5 policies (all analysable, no guards), 8 events,
12 actions (`Org.inviteMember` is the SPEC-DECLARATIONS worked example adapted to organizations,
plus `acceptInvite`, `createProject`, `createTask`, `rotateApiKey`, `removeMember`, `updateMemberRole`,
`Billing.handleStripeWebhook`, `createOrganization`, `revokeInvitation`, `archiveProject`, `createApiKey`),
4 queries, the `InviteFlow` workflow and the `Stripe` integration (webhook scheme `stripe`, raw body,
idempotent by event id). `averri.config.ts` lists the actor fixtures (`anonymous`, `owner`, `admin`,
`member`, `otherOrgAdmin`, `outsider`, `apiKeyMember`) whose headers resolve against the seed data.

The declarations are plain data and are not yet wired into the test suite (`observe()` from
`@averri/contracts` does that in the integration step). `test/averri-declarations.test.ts` checks that
they load, that every declared route exists, and that every fixture authenticates as its declared actor.

`src/averri.d.ts` (the `AverriTypes` augmentation `averri init` writes) is intentionally absent while this
example is compiled as part of the monorepo's single `tsc` program: a module augmentation here would
change `Actor` for every package. The declarations only use `actor.id` and `actor.email`, which the
default `Actor` type already permits.
